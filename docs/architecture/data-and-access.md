# データ・権限設計

Compass の実装に向けた設計要件。現行の library と Project_Knowledge は引き続き既存の保存・更新規則で運用し、実際に移行する範囲だけ切替時点を定める。
この文書の作成で既存データの正本や権限は変更されない。

## 統合後の正本

| 情報 | 統合後の正本 | 補足 |
|---|---|---|
| プロジェクト・参加者・権限 | 共有DB | 個人領域にもownerと権限を持たせる |
| 予算・施策・タスク・期限・提出 | 共有DB | 文書版と根拠へ関連付ける |
| 知識・方針のMarkdown本文 | サービスが管理する文書版 | 本文と版メタデータはDB、出力MDは編集用コピー |
| 原資料・添付 | 非公開のファイル保存領域 | 原本版は不変。ハッシュで照合する |
| 検索チャンク・索引 | 再生成できる派生データ | 文書版と権限に対応する |
| PyCharm用MD・台帳 | 版情報付き出力 | サーバの現在値と同時に独立更新しない |

同じ文書を複数のプロジェクト・施策・タスクから参照できる。
**共通文書も文書IDごとの更新先は一つ**とし、プロジェクトごとのコピーを独立した正本にしない。
共通文書をCompassへ切り替えたら、未移行プロジェクトは旧側を更新せず新しい正本を参照する。
実際の書込み停止とリンク案内は移行時に行い、設計文書だけを根拠に既存環境を書き換えない。

## 主なエンティティ

| 領域 | エンティティ案 | 関係の要点 |
|---|---|---|
| 組織と権限 | Organization, User, Group, Project, Membership, DocumentGrant | 参加権限と文書の個別許可を区別 |
| 図書館 | Document, DocumentRevision, FileBlob, ProjectDocument, Policy, Decision | 所属・参照・閲覧許可を分け、本文版と原本を保持 |
| 実行 | Initiative, MetricObservation, Task, TaskSubmission, Comment, Milestone | 施策とタスクの関連、担当者の提出と確認者の確認を区別 |
| 予算 | BudgetVersion, BudgetLine, ActualEntry, Allocation | 版・月次・科目と配賦元を保持し二重計上を防ぐ |
| 補助 | Notification, AuditEvent, ImportBatch, LegacyIdMap, AIProposal | 通知、変更、取込、旧ID、AI候補を追跡 |

内部IDは衝突しないUUID等を使用する案とし、従来のP/T/S番号は表示・出典用に保持する。
libraryのP001等と旧アプリのIDは異なる名前空間として対応表を作る。
改名・保存パス変更で文書IDや出典関係を失わない。
同じ内容でも出典・履歴・権限が違う文書を自動統合しない。物理blobを重複排除する場合も文書とACLは独立して保持する。

## 文書単独共有

プロジェクトへの参加と文書へのアクセスは別々に判定する。
プロジェクト未所属でも、明示的に共有された文書は閲覧・編集できる設計とする。
その許可を親プロジェクトの名称・予算・他文書へのアクセスに拡張しない。
文書へのリンクをタスクに追加しただけでは、タスク担当者の文書権限を変更しない。

アカウント停止・権限を管理する所属プロジェクトからの明示除外は、個人・グループの許可より優先する。
各文書がどのプロジェクトまたは個人領域の権限で管理されるかを一意に決め、複数プロジェクトからの参照はその管理元を変えない。
参照先プロジェクトの参加者であることだけで、共通文書の権限を自動拡張しない。
複数の許可・拒否が重なる場合は、既存ルールの挙動を調査し、有効権限の理由を説明できるようにする。

| 状況 | 期待する扱い |
|---|---|
| 本人の受け口・個人方針 | 初期は本人のみ閲覧可能 |
| プロジェクトに追加した資料 | 初期は作成者と当該プロジェクト管理者。共有操作で範囲を選ぶ |
| 未所属者への特定文書の共有 | 当該文書だけを許可。非公開の親プロジェクト情報を返さない |
| 明示除外・停止アカウント | 許可より拒否を優先 |
| 文書の「公開用」段階 | 配布用の版を意味し、閲覧範囲や匿名公開を変更しない |
| 組織管理者 | 運用権限だけで全資料の閲覧を許可しない |
| AIの参照 | 操作する利用者と同じ有効権限で判定 |

編集権限と共有先変更権限を分ける。
サーバ側の取得・保存・検索・履歴・添付・出力・通知・キャッシュに同じ権限判定を適用する。
権限を変更した場合、関連するAI成果物・引用・キャッシュの閲覧も再判定する。
私有情報を含むAI回答を共有チャットへ自動掲載しない。

## 原資料の保全

原資料は元名、バイト列、出典、取込日、ハッシュを保持する。
訂正・要約・分類は文書メタデータや整理済み知識に記録し、原資料の本文を書き換えない。
巨大なMDも切り捨てず原本を保存し、章単位の表示・抽出・検索は派生データとして扱う。
原資料に含まれるプロンプトや指示文は資料内容であり、権限・実行操作・送信先を変える命令として扱わない。

**原資料のMDへ識別用front matterを追記しない。**
取込・出力時の文書ID、版ID、内容ハッシュ、元パス等はmanifest側に保持する。
編集用に生成した知識MDへメタデータを付けることと、不変の原資料を変更することを区別する。

## PyCharmでの編集と再取込

1. 閲覧権限のある文書だけを、文書ID・元版ID・内容ハッシュを持つmanifestとともに出力する。
2. 図書館の可読性を維持したMD・相対リンクで、利用者がPyCharmから編集する。
3. 取込時に権限と変更差分を確認し、元版とサーバの現在版を照合する。
4. 版が一致した対象だけ更新候補を反映する。不一致なら競合として差分と再編集を提示する。
5. 削除・共有拡大・担当・金額・期限の変更は明示する。ローカルのファイル削除だけでサーバ文書を削除しない。

出力に含められない資料の名前・パスは、台帳・リンク・メタデータからも除外する。
ローカルのタスクや予算MDは共同利用中の正本ではない。取込できる項目を定義し、表示値やコメントから管理値を推定更新しない。
初期は知識本文の差分取込を優先し、業務値の変更はWebを基本にする。

## AIの提案と採用

AIは権限内の検索結果から必要箇所を取得し、文書ID・版ID・見出し/ページを出典として付ける。
古い情報・矛盾・根拠不足を表示し、本人の方針とAIの推測を分ける。
分類・方針・担当・期限・金額・共有範囲の候補は、採用操作まで業務の現在値を変更しない。
採用後は通常の権限付き更新として差分・採用者・根拠を履歴に残す。

AI停止中も権限付き検索と手動管理を利用できるようにする。
利用接続先・送信可能資料・費用上限は組織単位で定め、共有AIの既存停止方針を今回の基盤整備だけで解除しない。

# 既存環境と調査の根拠

Compass の新しい実装と、移行元の既存機能を区別するための記録。
Project_Knowledge と library の内容は、2026-09-29に図書館のP002へ記録した現状調査を継承したもの。
今回の文書整備では既存サーバーへの接続、実運用データの検証、既存アプリの試験再実行は行っていない。
既存文書の試験結果は、その文書に記録された結果として扱う。
元文書・コードの参照先は [参照資料一覧](sources.md)に集約している。

## Compass の開始点

本人が名称 **Compass** を採用し、PyCharmにDjangoプロジェクトを作成・アタッチ済み。
整備開始時に `manage.py`、`compass/`、`templates/`、`pyproject.toml`、`uv.lock` を確認した。
初期コードはDjango標準の管理画面とSQLiteによる基盤で、今回の作業はこれを維持して開発・文書環境を整える範囲。

予算・施策・タスク・共有認証・図書館・AI・移行処理は、Compassの実装済み機能として扱わない。
共有DBへの接続や原資料の移動・取込も未実施で、libraryとProject_Knowledgeの現在の更新先を変更していない。
採用経緯は [名称の決定](../decisions/0001-name.md)、次の実装段階は [ロードマップ](../planning/roadmap.md)を参照する。

## Project_Knowledge

既存READMEに記録された版は0.3.2。
Windowsの利用者端末でPythonのローカルHTTPアプリを動かし、ブラウザから利用する。
ローカルアプリが独立した共有サーバーへ接続し、Google Workspace社員認証とプロジェクト・文書単位の権限を利用する構成。

共有APIはOrigin付きPOSTを拒否する構成と調査されている。
共有URLへ直接ログインするWebサービスにするには、画面配信・認証セッション・CSRF対策・API接続経路を変更する必要がある。

| 項目 | 旧調査で確認された現状 | Compassで必要な追加 |
|---|---|---|
| プロジェクト | 個人・共有それぞれにプロジェクトと文書 | 共通ID、目的・責任者、業務管理への関連 |
| 文書 | TXT/MD/HTML、Office、PDF、原本履歴、本文検索 | 図書館取込、知識・方針・判断の関係、大容量資料 |
| 共有 | Google社員認証、社員・グループ、参加権限、ファイル単位共有 | ブラウザから直接利用する入口、指示・提出・確認 |
| 予算 | .pkbudget文書の月次予算・実績・差額。個人・共有で利用可能 | 施策配賦、構造化DB、予算版の明示 |
| タスク | READMEでは次フェーズ | 担当、期限、親子関係、結果提出、確認・差戻し |
| 施策・KPI | 構想・後続フェーズ | 目的、指標、期間、予算、関連タスク、振り返り |
| スケジュール | 後続フェーズ | タスク日付、マイルストーン、予定・実績の表示 |
| AI | 個人側で選択資料1〜8件、合計6万文字まで送信 | 権限内検索、図書館参照、整理提案と管理情報への関連 |
| 共有AI | 通常経路で外部AI送信を拒否 | 組織の利用方針に基づく設定・制御 |
| 外部編集 | ローカルは定期取込、保存時にハッシュで競合検知 | 版付き出力と差分取込によるWeb編集との両立 |

## library

初回取込記録と旧現状調査には、原資料60件、5,815,496 bytes、ハッシュ台帳・資料台帳・P001の整理枠が記録されている。
今回の設計文書整備によって原資料の件数・ハッシュを再検証したとは扱わない。
移行前には [移行計画](../migration/plan.md)に従って元資料の最新一覧を確定し、照合する。

- 最大MDは4,163,819 bytesで、既存アプリの2MiB上限を超える。
- 画像参照3件の実ファイル不足と、一部の文字化けが記録されている。
- 現在のタスク状態の正本はMDであり、共有DBへ切り替える範囲・時点を明示する必要がある。
- 事業分類・進捗・方針候補には未確認が含まれる。取込だけで確定値にしない。

## 再利用と変更の境界

原本保持、履歴・出典、抽出処理、予算の検証・計算、権限ルール、既存試験、画面で得た業務知識は再利用候補。
ローカル常駐を前提とした接続・認証、共同業務のデータモデル、保存層、検索・AI連携、ブラウザ向け入口は変更対象。

既存SQLiteを共有フォルダへ置いたり、共有サーバーのOrigin拒否だけを解除したりする方式で、共同利用の要件を満たしたとは判断しない。
設計上の確認点は [未決事項](../planning/open-questions.md)、実現すべき振る舞いは [受入条件](../requirements/acceptance.md)で追跡する。

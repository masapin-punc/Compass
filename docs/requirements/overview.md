# Compass 要件定義

本書は Project_Knowledge と図書館を統合する Compass の実装前要件である。
製品名 **Compass** と、その開発・設計文書をこのプロジェクトへ集約することは本人が採用した。
ユーザー作成済みの Django 基盤を利用する。下記の業務機能、PostgreSQL、データ移行は今後の実装・検証対象であり、稼働済みとは扱わない。
「既存」「現行」の記述は移行元の調査に基づく。Compassの実装済み機能を意味しない。

旧設計との対応は [参照資料](../reference/sources.md)、実装済みと構想の区別は [現状調査](../reference/current-state.md)、
構成は [構造設計](../architecture/structure.md)、検証基準は [受入条件](acceptance.md)を参照する。

## 1. 目的

プロジェクトに必要な知識と仕事を一つの場所で扱い、AIが情報の整理・検索・計画・振り返りを補助する。
メンバーは雑メモ・資料・依頼・結果を残せばよく、最初から分類や大量の項目入力を求めない。
予算・施策・タスク・スケジュール・資料・情報共有が同じプロジェクトIDでつながる。

「AIが知っている」とは、利用者が閲覧可能な資料・現在値を検索し、出典と情報時点を伴って回答できること。
すべての資料を毎回送ることや、モデルへ永続的に記憶させることを前提にしない。

## 2. 前提・未決事項

| 項目 | 初期設計の前提案 | 確認が必要な点 |
|---|---|---|
| 対象組織 | 既存方針を引き継ぎ社内1組織 | 利用人数、同時利用人数 |
| 利用端末 | PCのブラウザ、オンライン中心 | スマートフォンの利用頻度、オフライン必須か |
| 社外共有 | 初期対象外 | 将来必要なら認証・契約・公開範囲を別途設計 |
| 認証 | 現行のGoogle Workspace社員認証を継承 | 本番用認証設定 |
| AI | 許可された接続先・資料だけ利用 | 共有資料の外部送信可否、費用上限 |
| 会計 | プロジェクト管理用の予実管理 | 会計システム連携の必要性 |
| 編集 | Webで共同利用、PyCharmから版付き差分取込 | 常時自動同期やオフライン編集の必要性 |
| 運用 | 試行は既存Ubuntu環境を候補にする | 本番は自社運用か管理サービスか |

今回の設計によって既存の共有AI停止方針や社内限定条件を解除したことにはならない。
確認点の更新先は [未決事項](../planning/open-questions.md)とする。

## 3. 利用者と権限

| 役割 | 基本的な操作 |
|---|---|
| 組織管理者 | 社員・グループ・運用設定を管理。管理者であることだけで全資料閲覧権限を付けない |
| プロジェクト管理者 | 参加者、プロジェクト方針、依頼・確認、共有範囲を管理 |
| 編集メンバー | 許可された施策・タスク・文書を作成・更新、結果を提出 |
| 閲覧メンバー | 許可された内容を閲覧 |
| 予算担当 | 予算の閲覧・編集・確定権限を追加付与 |
| ファイル限定共有先 | 指定文書のみ閲覧・編集。他のプロジェクト情報へ権限を拡張しない |

依頼者・担当者・確認者はタスクごとの役割で、組織の肩書と分ける。
AIは操作した利用者の権限で動作し、管理者の権限を借りない。
権限の有無は画面だけでなく、サーバ側のすべての取得・更新で判定する。

アカウント停止・プロジェクトからの明示除外を許可より優先する。
個人・グループ・参加権限の重複は現行の規則を引き継ぎ、有効権限の理由を表示する。
編集権限と共有先を変更する権限を分ける。権限のない資料をタスクに添付しても、担当者へ自動的に閲覧権限を付けない。

個人の受け口・個人方針は本人のみが初期閲覧者。
プロジェクトの共有資料は現行同様、初期は作成者と当該プロジェクト管理者に限定し、共有操作で範囲を選ぶ。
組織管理者の運用権限とプロジェクト管理者の資料管理権限を区別する。

## 4. 機能要件

「初期」は6領域を一通り使える最小範囲。「後続」は拡張範囲を示す。

| ID | 領域 | 初期に実現する内容 | 後続 |
|---|---|---|---|
| FR-01 | プロジェクト | 名称・目的・責任者・期間・状態・メンバー・方針・概要画面 | 横断ポートフォリオ |
| FR-02 | 受け口 | 未分類メモ、TXT/MD/HTML・既存対応ファイルの取込、原本保持 | 独自録音・OCR・自動メール取込 |
| FR-03 | 予算 | 月次予算・実績・差額、予算版、科目、施策への配賦、元資料 | 会計連携、資金繰り、給与明細、感度分析 |
| FR-04 | 施策 | 目的・仮説・期間・担当・指標・予算・関連タスク・振り返り | 複雑なKPIツリー・効果帰属分析 |
| FR-05 | タスク | メイン/サブタスク、担当・依頼者・確認者・期限・完了条件・優先度・状態 | 複雑な依存関係と自動日程調整 |
| FR-06 | スケジュール | タスクの開始/期限/完了日、マイルストーン、期限一覧・カレンダー | 高度なガント・外部カレンダー同期 |
| FR-07 | 図書館 | 原資料、整理済み知識、方針、意思決定、資料台帳、検索、版・引用 | 意味検索の高度化 |
| FR-08 | メンバー共有 | 個人/グループ共有、依頼、コメント、メンション、結果提出、確認、アプリ内通知 | メール・Slack等の通知連携 |
| FR-09 | AI | 権限内検索、出典付き回答、要約、分類/タスク/方針候補、進捗要約 | 自律実行・定期提案 |
| FR-10 | 持出し・編集 | 権限内のMD/CSV出力、原本取得、ID・版付きMD差分取込 | リアルタイム共同編集、自動双方向同期 |
| FR-11 | 運用 | 操作履歴、バックアップ・復元、容量・ジョブ・AI費用の確認 | 複数組織へのサービス提供 |

### 4.1 予算

- プロジェクトごとに対象期間・通貨・会計年度起点・科目を設定する。初期通貨はJPY。
- 予算は版を持ち、下書き・確定・廃止を区別する。比較対象の確定版を明示する。
- 月次の予算・実績は固定小数で管理し、未入力と0を区別する。
- 差額は実績−予算。費用超過と売上上振れを同じ色・意味にしない。
- 費用の予算残額は予算−実績。施策への「配賦残」は予算−配賦額で別に表示する。
- 施策別金額は同じ予算科目・実績記録への配賦として表現する。プロジェクト合計へ二重加算しない。
- 配賦合計が元の金額を超える場合は確定を拒否する。未配賦分を見えるようにする。
- 取引単位の実績記録と既存の月次集計を同じ期間・科目で重複計上しない。
- 初期は既存月次実績を移行できればよい。取引明細を採用する場合は集計元を切り替える。
- 複数予算案を単純合算しない。科目変更・予算確定・実績修正は履歴に残す。
- 既存のGMV・寄付件数は指標として保持し、売上高へ加算しない。
- .pkbudgetと対応Excelをプレビューして取り込む。出典の名前・ハッシュ・範囲を保持する。
- AIは差異の説明や科目候補を提示する。金額の正本更新は通常の権限付き保存で人が確定する。

### 4.2 施策・タスク・結果

施策は「何を達成するために行うか」、タスクは「誰が何をいつまでに行うか」を表す。
施策のない通常業務タスクも登録できる。タグだけでこれらの関係を代替しない。

依頼の基本フロー:

1. 依頼者が目的・担当者・期限・完了条件・参考資料を登録する。
2. 担当者の「自分の仕事」とアプリ内通知へ反映する。
3. 担当者が着手し、進捗・不明点・添付資料を共有する。
4. 結果、成果物、必要なら実績値を提出する。
5. 確認者が確認済みにするか、理由を付けて差し戻す。
6. 結果を知識候補・次の施策へ関連付ける。

通知はアプリ内で保持し、未読・既読を区別する。通常の画面更新または30秒以内の定期取得で他メンバーの変更を反映する設計を初期案とする。
接続が切れた場合は未保存・再接続を表示し、ローカルで保存済みと誤認させない。

状態は「下書き→未着手→進行中→結果提出→確認済み」を基本とし、差戻し・保留・中止・未確認を追加する。
担当者による提出と、確認者による完了確認を区別する。
個人タスクでは本人が確認者を兼ねてよい。現行MDのdoneは履歴を確認せず確認済みに変換しない。

日付変更は履歴を残す。期限不明はnullとし、AIが推定した日付は候補表示する。
スケジュールはこの日付から生成し、同じ期限をカレンダーへ二重入力させない。
日付だけの期限と時刻付き予定を区別し、日時は保存時UTC・表示時組織タイムゾーンを基本にする。

### 4.3 知識・文書・方針

- 原資料と整理済み知識を分け、原資料のバイト列・元名・出典・取込日・ハッシュを保存する。
- 文書はファイルパスに依存しない固定IDを持ち、改名後もリンクと履歴を維持する。
- 1文書を複数プロジェクト・施策・タスクから参照できる。所属・参照・閲覧許可を区別する。
- 個人方針とプロジェクトの採用方針を区別し、共有は明示的に行う。
- 方針には適用範囲・確認日・根拠を、意思決定には理由・代替案・変更関係を残す。
- 未分類、整理中、知識、公開用は文書の整理段階。公開用という段階だけで閲覧範囲を広げない。
- 「公開用」は配布用の版を意味し、匿名のインターネット公開機能ではない。
- MD本文は版管理して保管し、元の版へ戻せる。検索索引は再作成可能にする。
- 図書館のAGENTS.mdは開発・整理作業の案内として保持する。業務アプリの権限設定の代替にしない。

### 4.4 AI

利用者の質問→権限による対象絞込→検索→必要箇所の取得→回答と出典、の順に処理する。
資料の引用は文書ID・版ID・見出し/ページを持ち、回答時に使用した原文を確認できる。

- 閲覧許可のない資料・予算・他人の個人方針を検索・生成の対象にしない。
- プロジェクト未所属でも明示的に共有された文書だけは参照できる。ただし所属プロジェクト名・他の資料へ参照範囲を拡大しない。明示除外は許可より優先する。
- 文書名・抜粋・履歴・添付・キャッシュ・出力ファイルも同じ権限範囲を守る。
- 私有情報を含む回答を、共有チャットや通知へ自動公開しない。
- 共有するAI成果物は、根拠資料を受け手が閲覧できるか確認する。必要なら私有情報を除いて再生成する。
- 参照権限が変わったら、関連する生成物・引用・キャッシュの閲覧も再判定する。
- 原資料中の指示文で権限・送信先・実行操作を変更しない。
- 根拠不足、古い資料、資料間の矛盾を示す。AIの提案を本人の採用方針と混同しない。
- 計画・担当・期限・共有範囲の提案は下書きとして保存し、採用操作で業務データに反映する。
- AIの利用先、許可資料、送信量、費用上限を組織単位で設定する。
- AI停止や障害時も、文書検索・手動編集・プロジェクト管理は利用できる。

## 5. データの関係と正本

予算・施策・タスク・参加者・権限は共有DB、文書本文は版管理された文書、原資料は不変の原本として管理する設計とする。
文書の所属、参照元、閲覧許可を分け、複数プロジェクトが参照する文書も更新先は文書IDごとに一つにする。
移行を実施するまでは既存環境の更新ルールを継続する。
エンティティ、正本の境界、文書単独共有、MD出力と取込の詳細は [データ・権限設計](../architecture/data-and-access.md)を参照する。

## 6. 非機能要件

- メンバー間の共有状態はサーバで一元管理し、端末同士の同期を必須にしない。
- 同時更新は版番号照合で検出し、先の保存を無条件上書きしない。差分と再編集を提示する。
- 保存、予算修正、担当・期限変更、権限変更、AI提案の採用を追跡できる。
- 原資料のアップロードと抽出・索引作成を分け、失敗しても原本を失わない。
- アップロードの受信上限・保存上限・抽出上限・索引上限を別々に定義する。
- 初期の容量目標案: MD/TXT原本10MiB以上、Office/PDFは既存20MiB以上を維持。
  4,163,819 bytesの既存MDを原文のまま保存できることを必須とする。
- 大容量文書は章単位表示・検索チャンクで扱い、AIへ全文投入しない。
- バックアップはDB・原本版・設定の復元手順を一組として管理する。索引は再構築可能とする。
- 日次バックアップ、RPO 24時間以内・RTO 4時間以内を初期提案値とし、本番運用条件に合わせて確定する。
- 権限のない原資料を静的URLやバケット一覧から取得できないこと。
- 初期性能評価案: 同時利用20人・資料1万件で通常画面3秒以内、検索5秒以内を目標にする。
  これは実測・保証値ではない。AIと大容量取込は非同期の進捗表示を別に評価する。
- APIキー等はサーバの秘密設定で管理し、Gitや配布MDへ含めない。
- 原本・MD・CSV・ID対応表を出力でき、サービスの利用終了後も資料を取り出せる。

## 7. 最小の画面構成

- 自分の受け口: 雑メモ・資料追加、AIの整理候補。
- 自分の仕事: 依頼された作業、期限、差戻し、結果提出。
- プロジェクト: 概要、施策、タスク、スケジュール、予算、図書館、メンバー。
- 図書館: 原資料・知識・方針・意思決定、検索と出典表示。
- AI相談: 対象プロジェクトと参照範囲を表示する相談画面。
- 通知: 依頼、メンション、結果提出、確認結果。
- 管理: メンバー、グループ、AI利用、運用情報。

フォルダ名、DBテーブル名、内部IDの入力を通常利用者の作業にしない。

## 8. 受入条件

機能・移行・権限の確認シナリオは [受入条件](acceptance.md)で管理する。
文書サイトのビルド成功や Django の起動だけで、業務機能の受入完了としない。

## 1. 最初の要望: 大量のMDを「図書館」として整理したい

本人は、複数プロジェクトに関する多数のMDを持っている。
これらには、知識、構想、検討資料、本人の方針、メインタスク、サブタスクが含まれる。

目的は次のとおりだった。

- プロジェクトやディレクトリ構造をAGENTS.mdで説明し、AIが対象をたどれるようにする。
- プロジェクト単位の知識と、本人なりの方針・方向性を整理する。
- PyCharmでファイルを管理する。
- この情報基盤を「図書館」と呼ぶ。

最初の案は「プロジェクト→メインタスク→サブタスク」のディレクトリ分類だった。
検討の結果、同じ資料が複数タスクの根拠になること、古い提案と現在の方針が混ざることから、
**原資料・整理済み知識・本人の方針・判断経緯・実行タスクを分け、リンクでつなぐ**方針になった。
厳密な3階層制限や、完了のたびのディレクトリ移動は採用しなかった。

## 3. 次の要望: Project_Knowledgeと統合したい

本人はD:/projects/Project_Knowledgeとの構想統合を求めた。
Project_Knowledgeが図書館の知識を利用し、AIが次の6領域を補助することを目指している。

1. 予算管理。
2. 施策管理。
3. タスク管理。
4. スケジュール管理。
5. 資料・ドキュメント管理。
6. 同じプロジェクトのメンバーとの情報共有。

共有とは閲覧だけではなく、**依頼・指示→担当者の実行→結果提出→確認・差戻し**まで含む。
担当者が作業を終えたことと、確認者が結果を確認したことを区別する。

本人は既存のサーバー・クライアント方式について「管理手法がもっと楽な方がよかった」「単純なWebサービスでよいかもしれない」と述べた。
当初の依頼範囲は、要件定義、最適なディレクトリ・プロジェクト構造、新名称の提案だった。

## 4. 既存Project_Knowledgeを調べて分かったこと

旧調査時の版は0.3.2。専用のWindows配布アプリがローカルHTTPサーバーを起動し、画面自体はブラウザで表示する。
そのローカルアプリを介して中央の共有サーバーへ接続する構成だった。

| 領域 | 既存側で確認・記録されていたこと |
|---|---|
| 文書 | TXT/MD/HTML、Office、PDFの原本・本文・履歴・検索 |
| 共有 | 社員認証、グループ、プロジェクト参加と文書単独共有 |
| 予算 | .pkbudget形式の月次予算・実績・差額、共有・履歴、特定Excelの取込 |
| AI | 個人側で選択した1〜8資料、合計6万文字以内を利用 |
| 共有AI | 通常利用では外部AI送信を停止 |
| タスク・施策・KPI・予定 | 主に構想または後続フェーズ |

この表はCompassの完成機能一覧ではない。既存サーバーへの接続や、実運用データの検証は行っていない。
コードと資料の根拠は[現状調査](../reference/current-state.md)にある。

特に次の制約が統合設計に影響した。

- 共有APIはOrigin付きPOSTを拒否しており、ブラウザから直接利用するには認証・画面配信・通信経路の変更が必要。
- テキストの2MiB上限は、図書館の約4MBのMDを扱えない。
- 外部編集とWeb共有編集を自動同期すると、版・権限・競合の運用が増える。
- 原構想は「雑に書く」「整理を強制しない」「原文を残す」「情報とタスクをつなぐ」を重視する。

既存の抽出、原本保持、予算計算、権限ルール、試験は再利用候補。
単にOrigin拒否を解除することや、SQLiteを共有フォルダへ置くことを統合案にはしていない。

## 5. 統合設計として提案したこと

図書館のP002「知識・プロジェクト管理統合」に初期設計を作成した。

- 中央Webサービスをブラウザから利用し、端末ごとの配布・更新・接続設定を減らす。
- 一つのPythonアプリ内を責務別に分け、初期から多数のサービスに分割しない。
- 共同管理の現在値と権限は共有DB、原資料は変更しない版として保持する。
- 原資料・知識・方針・意思決定・予算・施策・タスクを固定IDで結び付ける。
- ローカルMarkdownは版付き出力と差分取込で利用し、自動双方向同期を初期必須にしない。
- AIは閲覧権限のある情報を検索し、出典・版・情報時点を伴って回答する。
- AIの分類や提案を、共有許可・本人の方針・金額・担当・期限の確定と混同しない。

Web方式もサーバー・クライアント方式であり、ブラウザがクライアントになる。
「図書館の知識をAIが知っている」は、必要な根拠を取得できることを意味する。
全資料を毎回送ること、モデルに永続記憶させることを要件にしていない。

## 8. 検討中に明確化した重要な整合条件

1. **文書単独共有**: プロジェクト未参加でも、明示共有された文書だけは参照できる。
   参加していないという理由で一律拒否しない一方、プロジェクト名・予算・他文書を公開しない。
2. **拒否の優先**: アカウント停止、管理元プロジェクトからの明示除外を許可より優先する。
   関連先プロジェクトを追加しただけで権限を変更しない。
3. **原本不変**: 原資料MDに識別用front matterを追記しない。ID・版・ハッシュはmanifest等に保持する。
4. **正本は一つ**: 複数プロジェクト共通の文書も、文書IDごとの更新先を一つにする。移行途中も二重更新しない。
5. **個人と共有**: 本人の私有方針を共有方針に自動昇格させない。私有情報を用いたAI回答も自動共有しない。
6. **権限の範囲**: 一覧、本文、題名、検索、添付、履歴、AI、引用、通知、キャッシュ、出力で一貫させる。
   組織管理者を無条件の全資料閲覧者にはしない。
7. **予算の区別**: 未入力と0、GMVと売上、配賦と総予算、月次集計と取引明細を混同しない。
8. **作業状態の区別**: 担当者の結果提出と確認者の確認済みを分け、旧doneを自動的に確認済みに変換しない。
9. **整理段階と公開**: 「公開用」という資料の段階は匿名公開の許可を意味しない。
10. **未確認を保持**: 古い予定、提案、本人の未確認方針を新システムの確定値に変換しない。
